# Macnman Firmware Repository

This repo manages the folder structure and firmware binaries for Macnman devices.
Each device folder holds its firmware image (`.bin`) and product photo (`.png`), and
`LoRaWAN/sensors_v1.json` is the single manifest that describes every device so the OTA /
provisioning tool can locate the right file.

The manifest lives at `LoRaWAN/sensors_v1.json` for historical reasons but covers **every**
device in the repo, including the `LoRa/`, `Cellular/` and `Wi-Fi/` ones outside the `LoRaWAN/` tree.
The four protocol trees — `LoRaWAN/`, `LoRa/`, `Cellular/` and `Wi-Fi/` — are siblings at the repo root,
so a device's `binpath` starts with whichever tree it belongs to.

Empty folders contain a `.gitkeep` file, because git cannot track a truly empty directory.
Delete the `.gitkeep` when real firmware is added to that folder.

`MY_L1_CO2_X1`, `MY_L1_SPH_X1`, `MY_L1_OD_X1` and `MY_L1_LPS28_X1` use Macnman's `MY-` model numbers: the manifest key has

key rather than `ModelNumber`, so anything matching the device-reported model must accept both forms
(the Maya app does: `_` and `-` count as the same and case is ignored).

#### `MY_L1_LPS28_X1` notes

Battery-powered LoRaWAN node with an ST LPS28DFW absolute pressure sensor on I2C. It reports
`Pressure` (hPa) and `Temperature` (°C) plus battery level, and announces `DEVTYPE=PRESSURE`.
`DEVINFO` reports application `V1.0.0`. Sampling and threshold-trigger settings can be set per
parameter (`Pressure`, `Temperature` or `Both`).

#### `MacSync_LPS_ToF_X1` version notes

| Version | File | What it contains |
|---|---|---|
| V1.0.0 | `MacSync-LPS-ToF-X1.bin` | Standard build. Entry, exit and occupancy counters are **cumulative** — they keep incrementing across uplinks and are only cleared on a power cycle or an explicit reset command, so each uplink carries a running total. |
| V1.0.1 | `custom/MacSync-LPS-ToF-X1-V1.0.1.bin` | Non-standard build. **Resets entry, exit and occupancy in every uplink** — after the payload is built and sent, all three counters are cleared to zero, so each uplink reports only what happened since the previous uplink: an interval count, not a running total. Everything else (ToF sensing, I2C interface, LoRaWAN join and payload layout) is the same as V1.0.0. |

Both versions run on the same hardware and share the one product photo,
`MacSync-LPS-ToF-X1.png`. V1.0.1 sits in `custom/` because it is a non-standard build — see
[the `custom/` folder rule](#the-custom-folder) below.

> **Payload meaning changes between these two versions.** Anything decoding the uplink —
> network-server decoder, dashboard, database — must know which version a unit is running:
> V1.0.0 counts must be differenced to get an interval, V1.0.1 counts must be summed to get
> a total. Flashing V1.0.1 onto a unit whose backend assumes V1.0.0 will produce wrong
> numbers without any error.

The keys use underscores but the folders and files use hyphens, so read paths from the
manifest rather than building them from the key. For every datalogger `ModelNumber` is the
hyphenated form — `MY-W1D-SS7-X1`, `MY-W1D-TH-X1`, `MY-W1D-RTD-X1`, `MY-W3D-WEC-X1`,

`MY_W1D_TH_X1` firmware reports `MY_W1D_TH_X1`, matching the key rather than `ModelNumber`.
The RTD, WEC and WPH firmware report the hyphenated model as a fixed `DEVTYPE`
(`DEVTYPE=MY-W3D-WPH-X1`). `MY_W3D_WEC_X1` and `MY_W3D_WPH_X1` are the first `W3D` devices:
DC 24 V powered Wi-Fi dataloggers. Their version string is `V1.0`, two parts, the same style
as the `V1.1` of `MY_W1D_TH_X1`.

`MY_W1D_TH_X1` runs on the same hardware as the Wi-Fi sensor `MS_WBSD_TH_X1`. V1.1 has its OTA
address built in —
`raw.githubusercontent.com/MacnMan/macnman_firmware-s/main/Wi-Fi/Datalogger/MY-W1D-TH-X1/MY-W1D-TH-X1.bin`
— so every release must be uploaded to exactly that path. Units still running the 2026-10-09
firmware only know `Wi-Fi/Sensors/MS-WBSD-TH-X1/MS-WBSD-TH-X1.bin`; to move them to a new
release over MQTT OTA, a copy of it has to sit at that path too.

There are no LoRaWAN dataloggers, so there is no `LoRaWAN/dataloggers/` folder: the RS485 / analog
device `MY_L1_CV_X1` is in `sensors/` because it does not store readings in its flash memory.
A device that logs readings to flash
gets `D` after the power digit (e.g. `MY-L1D-TH-X1`); create `LoRaWAN/dataloggers/` for the first one.

from the repo and the manifest. Three things about them differ from the rest of the repo:

- Their **manifest keys use hyphens** (`MS-L35-CT-X1`, `MS-L3-CT-X2`), the same as their folders
  and `ModelNumber`, instead of the underscore keys used everywhere else.
- Their **`.bin` carries the version in its name** (`MS-L35-CT-X1-V1.0.2.bin`,
  `MS-L3-CT-X2-V1.0.0.bin`) and sits at the top level of the device folder, not in `custom/`.

  does not identify a build; check the commit.

  `controller2` with the older layout. The manifest says `node` for all three.

`35` in `MS-L35-CT-X1` is not a single power digit on the nomenclature sheet. The folders hold only
the `.bin` and the `.png`; the earlier `README.md` files and the LX2 codec were removed from them.

## Naming Convention

All new devices use the **Macnman model number nomenclature** (Macnman Technologies Pvt. Ltd.):

```
Family - Communication + Power + Storage - Function - Hardware revision

  MS   -   L    1    D   -   TH   -   X1
  |        |    |    |       |        |
  |        |    |    |       |        +-- hardware revision (X1, X2, ... Xn)
  |        |    |    |       +----------- function (application / device)
  |        |    |    +------------------- D = datalogger (flash present); no letter = no flash
  |        |    +------------------------ power type (1-5)
  |        +----------------------------- communication protocol (L, M, C, W, B)
  +-------------------------------------- product family (MS, MY, ML)
```

| Field | Code | Meaning |
|---|---|---|
| Product family | `MS` | MacSet |
| | `MY` | MacSync |
| | `ML` | MacLink (gateway) |
| Communication protocol | `L` | LoRaWAN |
| | `M` | MacTalk (raw LoRa, point-to-point) |
| | `C` | Cellular |
| | `W` | Wi-Fi |
| | `B` | BLE |
| | two letters | Two radios, primary first — e.g. `LB` = LoRaWAN + BLE, `LC` = LoRaWAN + Cellular |
| Power type | `1` | Battery |
| | `2` | Solar + Battery |
| | `3` | DC 24 V |
| | `4` | PoE |
| | `5` | Mains (AC) |
| Data storage (optional) | `D` | Datalogger — flash present |
| | *(none)* | No flash |
| Function — sensors | `TS` | Temperature |
| | `TH` | Temperature + Humidity |
| | `PS` | Pressure |
| | `WS` | Weather Station |
| | `US` | Ultrasonic |
| | `GS` | Gas |
| Function — devices | `CV` | Converter |
| | `CT` | Controller |
| | `BN` | Beacon |
| | *(none)* | MacLink gateways have no function code |
| Hardware revision | `X1`, `X2` … `Xn` | Revision 1, 2 … n |

The firmware version is **not** part of the model number — it lives in `versions[].application`
in the manifest (see [Adding a New Version to an Existing Device](#adding-a-new-version-to-an-existing-device)).

(Wi-Fi dataloggers) and `MY-W1-CV_X1` (Wi-Fi sensor).

Function codes used here that are **not on the nomenclature sheet**: `NS` (noise / sound),
`CO2` (CO2 + temperature + humidity), `SPH` (pH), `OD` (odor — NH3 / H2S), `LPS28` (pressure + temperature,
named after the LPS28DFW part rather than the sheet's `PS` pressure code), `SS7` (7-parameter soil sensor),
`RTD` (PT100 temperature probe), `WEC` (water conductivity), `WPH` (water pH), `SD` (sound
detection) and `DRS` (door / reed switch). They sit in the function position like the sheet's codes, but
the sheet does not list them yet. The power position of `MS-L35-CT-X1` holds `35`, which is not a
single digit from the power table either.

In the manifest, the key uses underscores (`MY_L1_TH_X1`) while the folder, files and
`ModelNumber` use the hyphenated model number (`MY-L1-TH-X1`). New devices should do the same.

Folder names use hyphens (`MY-L1-TH-X1`). File and JSON key names use either hyphens or
underscores depending on when they were added — see the mismatch note in [Known Issues](#known-issues).

Interface types used in the manifest: **I2C**, **RS485**, **RS485 & Analog** (the converters), **Analog**, **Digital**.

## Manifest — `LoRaWAN/sensors_v1.json`

Supports multiple firmware versions per device under a `versions` array.

```json
"MY_L1_CV_X1": {
  "devicetype": "node",
  "protocol": "LoRaWAN",
  "ModelNumber": "MY-L1-CV-X1",
  "type": "RS485 & Analog",
  "switchTo": [],
  "versions": [
    {
      "application": "V1.0.0",
      "releaseDate": "2026-11-04",
      "binpath": "LoRaWAN/sensors/MY-L1-CV-X1/MY-L1-CV-X1.bin",
      "photopath": "LoRaWAN/sensors/MY-L1-CV-X1/MY-L1-CV-X1.png"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `devicetype` | `node` for sensors and controllers, `datalogger` for loggers. The Maya app shows it but does not act on it |
| `protocol` | Radio protocol — `LoRaWAN`, `LoRa` (point-to-point), `Cellular` or `Wi-Fi`. The app uses it for `switchTo` only: a model with another protocol is never offered. (The app's own document spells the last one `WiFi`; this file uses `Wi-Fi` consistently, which is all that matters) |
| `ModelNumber` | The model the firmware is for — exactly the text the firmware sends as the third `DEVINFO` value: the hyphenated model number (`MY-L1-CO2-X1`) for `MY-` / `MS-` devices, the key itself for the older `MacSync_…` and `MS_WBSD_TH_X1` entries. Called `sensorName` until 2026-11-25 (commit `1724bc9`); the app reads `ModelNumber` and falls back to the key |
| `switchTo` | Model numbers a unit of **this** model may be switched to — same hardware, other function — written with dashes and in quotes, e.g. `["MY-C2-TH-X1"]`. The target model needs its own entry with the same `protocol`. `[]` = none; every entry has `[]` today. Called `installOn` for one day (2026-11-25, commit `44f524a`) before commit `225c41d` renamed it; the app still reads both |
| `type` | Hardware interface — `I2C`, `RS485`, `RS485 & Analog`, `Analog`, `Digital`. Shown as chips on the firmware card |
| `versions[].application` | Firmware version string, e.g. `V1.0.0`; shown on the card as `FV1.0.0`, newest on top |
| `versions[].releaseDate` | Date of that build, `YYYY-MM-DD` (added 2026-11-25, commit `ba94bbb`); shown as "Released 4 Nov 2026" |
| `versions[].binpath` | Repo-relative path to the `.bin` |
| `versions[].photopath` | Repo-relative path to the `.png` |

Entries: `MY_L1_TH_X1`, `MY_L1_NS_X1`, `MacSync_LPS_ToF_X1`,
`MacSync_LBS_ToF_X1`, `MY_L1_CV_X1`, `MY_L1_CO2_X1`, `MY_L1_SPH_X1`, `MY_L1_OD_X1`, `MY_L1_LPS28_X1`,
`MY_M1_DRS_X1`, `MY_M1_TH_X1`, `MY_M3_CV_X1`, `MY_C2_CV_X1`, `MY_C2_SD_X1`, `MS_WBSD_TH_X1`, `MY_W1D_SS7_X1`,
`MY_W1D_TH_X1`, `MY_W1D_RTD_X1`, `MY_W3D_WEC_X1`, `MY_W3D_WPH_X1`, `MY_L3_CV_X1`, `MY_W1_CV_X1`,
`MS_L5_CT_X1`, `MS-L35-CT-X1`, `MS-L3-CT-X2`. Every path in the manifest resolves to a real
file. `MacSync_LPS_ToF_X1` is the only device with more than one entry in `versions` — V1.0.0
and V1.0.1; see its version notes above for the difference. Every entry carries `switchTo: []`.

How the Maya app uses this file is written up in the Maya repo, `docs/Firmware_List.md`
(version 1.2, 2026-11-26). In short: the app reads the model number from the connected
device's `DEVINFO`, lists every version of the entry whose `ModelNumber` matches (`_` and `-`
count as the same, case is ignored), plus every version of the models in that entry's
`switchTo` that share its `protocol`, marked "changes the model". Units on older firmware
that send no model number are mapped by their old sensor name (`MS_LBS_TH_X1` → `MY-L1-TH-X1`,
`MS_LBS_NS_X1` → `MY-L1-NS-X1`); units that send `RS485` / `ANALOG` there get nothing, except
`controller8`, which maps to `MS-L3-CT-X2`. An invalid JSON file empties Push Firmware for
everyone, so validate before pushing. Never rename or delete an entry, or remove a version, that
units in the field still have.

### Use with BLE OTA

The firmware host app fetches this manifest, shows the user the device list, then downloads
`binpath` for the chosen version and pushes it to the device over BLE DFU. For that flow:

- `binpath` must be the **raw application image** the bootloader expects — a plain `.bin`,
  not a `.hex`, `.zip` or signed package. If your BLE stack needs a packaged image, add it
  alongside and point `binpath` at the package instead.
- `protocol` describes the device's **data radio** (`LoRa` / `LoRaWAN` / `Cellular` / `Wi-Fi`), not the OTA
  transport. BLE is the update channel for every device here.
- `application` is what the app compares against the version reported by the device to
  decide whether an update is offered — keep it accurate and bump it on every release.

> The old flat-format `sensors.json` (one version per device, no `versions` array) was
> removed. `sensors_v1.json` is now the only manifest — any tool still reading
> `sensors.json` must be pointed at it.

## Adding New Firmware

1. Create the device folder in the tree for its radio:
   - **LoRaWAN** → `LoRaWAN/<category>/<Device-Folder>/`, where category is `sensors`,
     `dataloggers` or `controllers`.
   - **raw LoRa** → `LoRa/<Device-Folder>/` — a flat, top-level tree with no category level.
   - **Cellular** → `Cellular/<Device-Folder>/` — flat, like `LoRa/`.
   - **Wi-Fi** → `Wi-Fi/Sensors/<Device-Folder>/` or `Wi-Fi/Datalogger/<Device-Folder>/`.
2. Drop in `<Device-Name>.bin` and `<Device-Name>.png`.
3. Add an entry to `LoRaWAN/sensors_v1.json` using the schema above, with `switchTo: []` and a
   `releaseDate` on the version. For a new version of
   an existing device, append to that device's `versions` array instead of adding a new key.
4. Check that `binpath` and `photopath` match the real files exactly — paths are
   case-sensitive on the server and start at the repo root (`LoRaWAN/...`, `LoRa/...`,
   `Cellular/...` or `Wi-Fi/...`).
5. If the folder previously held only a `.gitkeep`, delete that placeholder.
6. Commit both the binaries and the manifest change together.

### Adding a New Version to an Existing Device

A build that runs on the same hardware but behaves differently — changed uplink content,
changed reset behaviour, order-specific defaults — is a **new version of that device**, not
a new model. Keep the model number as it is and add to the `versions` array:

1. **Model number never changes.** No suffix in the JSON key or in `ModelNumber` —
   `MacSync_LPS_ToF_X1` stays `MacSync_LPS_ToF_X1`. The version string is the only thing
   that separates the builds.
2. **Bump the version** — `V1.0.0` → `V1.0.1` for a behaviour change on the same hardware.
   Append a new object, with its own `releaseDate`, to that device's `versions` array; leave the existing entries alone
   so units already in the field can still be matched to the image they are running.
3. **Never overwrite** an existing `.bin` in place — a rebuild gets the next version number
   and its own file.
4. **Photo** — reuse the device's existing `.png` when the hardware is identical; point
   `photopath` at that file rather than duplicating the image.
5. **Write down what the version contains** — add a row to that device's *version notes*
   table in this file, stating exactly how the behaviour differs. Nothing inside a `.bin`
   says what makes it special, so an undocumented build is unusable a few months later.
6. **Flag payload changes.** If the new version changes what the uplink bytes mean, say so
   in the version notes — the decoder and dashboard have to be told which version a unit is
   running.

### The `custom/` Folder — Non-Standard Builds Only

Each device folder may hold a `custom/` subfolder. **Only non-standard firmware goes in
it**; the shipping firmware always stays at the top level of the device folder, so the two
are never mixed up.

1. **Location** — `<Device-Folder>/custom/<Standard-Name>-<Version>.bin`, inside whichever
   tree the device lives in, e.g.
   `LoRaWAN/sensors/MacSync-LPS-ToF/custom/MacSync-LPS-ToF-X1-V1.0.1.bin` or
   `LoRa/MY-M3-CV-X1/custom/MY-M3-CV-X1-V1.0.1.bin`.
2. **File name** — letters, digits, `-`, `_` and `.` only. **No spaces and no brackets.**
   `binpath` is fetched as a URL by the OTA app, so a name with a space or a `(` in it
   breaks the download. Rename such a file to the `<Standard-Name>-<Version>.bin` form
   before adding it to the manifest.
3. **Still the same model** — a `custom/` build keeps the device's model number and is
   listed as a version of that device in the manifest, with `binpath` pointing into
   `custom/`. The folder is how a human tells standard from non-standard at a glance; the
   version string is how the app tells them apart.
4. **Always document it** in that device's *version notes* table — a `custom/` build with no
   written description is unusable later.

Because every version of a device sits in one `versions` array, the app can offer a
`custom/` build for any unit of that model. Check the version notes before flashing. If a
build must never reach ordinary units at all, it needs its own model number rather than a
version bump.

## Known Issues

**Hyphen vs. underscore inconsistency.** JSON keys use underscores while folders and file
names use hyphens (`MY_L1_TH_X1` → `MY-L1-TH-X1/MY-L1-TH-X1.bin`). Exceptions on both sides:
the folder `Wi-Fi/Sensors/MY-W1-CV_X1/` ends in `_X1`, and the controller keys `MS-L35-CT-X1`
and `MS-L3-CT-X2` use hyphens. Not a bug today because every path is written
out explicitly, but it will break any code that derives a path from a device name. The
Wi-Fi tree also capitalises its category folder (`Wi-Fi/Sensors/` vs. `LoRaWAN/sensors/`),
and the `LoRa/` and `Cellular/` trees have no category level
at all, so a path cannot be assembled from a device name and protocol alone — read it from
the manifest.

**`LoRa/` moved out of `LoRaWAN/`.** Raw-LoRa firmware used to live at `LoRaWAN/LoRa/` and
now lives in the top-level `LoRa/`. `sensors_v1.json` has been updated, but anything holding
a cached or hard-coded `LoRaWAN/LoRa/...` path — an older copy of the manifest, a script, a
CDN entry — still points at the old location and will fail to fetch.

**Renaming a device.** Rename the folder, the files and the manifest key and paths in the same
commit, and check that every path resolves: a path that does not exist gives the app a 404 for
the photo and the firmware. Anything holding an old key or path must reload the manifest.
