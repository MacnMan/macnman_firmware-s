# Macnman Firmware Repository

This repo manages the folder structure and firmware binaries for Macnman devices.
Each device folder holds its firmware image (`.bin`) and product photo (`.png`), and
`LoRaWAN/sensors_v1.json` is the single manifest that describes every device so the OTA /
provisioning tool can locate the right file.

---


The manifest lives at `LoRaWAN/sensors_v1.json` for historical reasons but covers **every**
device in the repo, including the `LoRa/` and `Wi-Fi/` ones outside the `LoRaWAN/` tree.
The three protocol trees — `LoRaWAN/`, `LoRa/` and `Wi-Fi/` — are siblings at the repo root,
so a device's `binpath` starts with whichever tree it belongs to.

Empty folders contain a `.gitkeep` file, because git cannot track a truly empty directory.
Delete the `.gitkeep` when real firmware is added to that folder.

|---|---|---|---|---|

| `MacSync_LBS_NS_X1` | RS485 | Noise / sound level | V1.0.0 | `.bin` (104.4 KB), `.png` |
| `MacSync_LBS_ToF_X1` | I2C | Distance / level (Time-of-Flight) | V1.0.0 | `.bin` (97.3 KB), `.png` |
| `MacSync_LPS_ToF_X1` | I2C | Distance / level (Time-of-Flight), people counting | V1.0.0, V1.0.1 | `.bin` (96.9 KB each), `.png` |

#### `MacSync_LPS_ToF_X1` version notes

| Version | File | What it contains |
|---|---|---|
| V1.0.0 | `MacSync-LPS-ToF-X1.bin` | Standard build. Entry, exit and occupancy counters are **cumulative** — they keep incrementing across uplinks and are only cleared on a power cycle or an explicit reset command, so each uplink carries a running total. |
| V1.0.1 | `custom/MacSync-LPS-ToF-X1-V1.0.1.bin` | Non-standard build. **Resets entry, exit and occupancy in every uplink** — after the payload is built and sent, all three counters are cleared to zero, so each uplink reports only what happened since the previous uplink: an interval count, not a running total. Everything else (ToF sensing, I2C interface, LoRaWAN join and payload layout) is the same as V1.0.0. |

Both versions run on the same hardware and share the one product photo,
`MacSync-LPS-ToF-X1.png`. V1.0.1 sits in `custom/` because it is a non-standard build — see
[the `custom/` folder rule](#the-custom-folder) below.

> **Payload meaning changes between these two versions.** Anything decoding the uplink —
> network-server decoder, dashboard, database — must know which version a unit is running:
> V1.0.0 counts must be differenced to get an interval, V1.0.1 counts must be summed to get
> a total. Flashing V1.0.1 onto a unit whose backend assumes V1.0.0 will produce wrong
> numbers without any error.

## Naming Convention

```
MacSync - L B S - TH - X1
   |      | | |    |    |
   |      | | |    |    +-- hardware revision (X1, X2, ...)
   |      | | |    +------- measurement / payload (TH, NS, ToF, DRS, STD, PO)
   |      | | +------------ S = Sensor, D = Datalogger
   |      | +-------------- B = Battery powered, P = externally Powered
   |      +---------------- L = LoRaWAN, M = raw LoRa (point-to-point)
   +----------------------- product family
```

Example of the raw-LoRa radio letter: `MacSync_MBS_DRS_X1` — **M**BS = raw LoRa, Battery
powered, Sensor.

Wi-Fi devices do not use the single-letter radio code. They spell the radio out and put the
power/role letters after the measurement: `MacSync_WiFi_TH_BS_X1` — Wi-Fi radio, **TH**
measurement, **B**attery powered **S**ensor, hardware revision X1.

Product families:

| Prefix | Meaning |
|---|---|
| `MacSync` | Sensor / datalogger nodes that report data |
| `MacSet` | Controllers that drive outputs |
| `MacTalk` | Legacy raw LoRa point-to-point devices. No current firmware — new raw-LoRa devices are named `MacSync` with `M` in the radio position. |

Folder names use hyphens (`MacSync-LBS-TH`). File and JSON key names use either hyphens or
underscores depending on when they were added — see the mismatch note below.

Interface types used in the manifest: **I2C**, **RS485**, **Analog**, **Digital**.

## Manifest — `LoRaWAN/sensors_v1.json`

Supports multiple firmware versions per device under a `versions` array.

```json
"MacSync_LBD_STD_X1": {
  "devicetype": "datalogger",
  "protocol": "LoRaWAN",
  "sensorName": "MacSync_LBD_STD_X1",
  "type": "RS485",
  "versions": [
    {
      "application": "V1.0.0",
      "binpath": "LoRaWAN/dataloggers/MacSync-LBD-STD/MacSync-LBD-STD-X1.bin",
      "photopath": "LoRaWAN/dataloggers/MacSync-LBD-STD/MacSync-LBD-STD-X1.png"
    }
  ]
}
```

| Field | Meaning |
|---|---|
| `devicetype` | `node` for sensors, `datalogger` for loggers |
| `protocol` | Radio protocol — `LoRaWAN`, `LoRa` (point-to-point) or `Wi-Fi` |
| `sensorName` | Display name (currently same as the key) |
| `type` | Hardware interface — `I2C`, `RS485`, `Analog`, `Digital` |
| `versions[].application` | Firmware version string, e.g. `V1.0.0` |
| `versions[].binpath` | Repo-relative path to the `.bin` |
| `versions[].photopath` | Repo-relative path to the `.png` |

Entries: `MacSync_LBS_TH_X1`, `MacSync_LBS_NS_X1`, `MacSync_LPS_ToF_X1`,
`MacSync_LBS_ToF_X1`, `MacSync_LBD_STD_X1`, `MacSync_MBS_DRS_X1`, `MacSync_MBS_TH_X1`,
`MacSync_MPV_X1`, `MacSync_WiFi_TH_BS_X1`. Every path in the manifest resolves to a real
file. `MacSync_LPS_ToF_X1` is the only device with more than one entry in
`versions` — V1.0.0 and V1.0.1; see its version notes above for the difference.

### Use with BLE OTA

The firmware host app fetches this manifest, shows the user the device list, then downloads
`binpath` for the chosen version and pushes it to the device over BLE DFU. For that flow:

- `binpath` must be the **raw application image** the bootloader expects — a plain `.bin`,
  not a `.hex`, `.zip` or signed package. If your BLE stack needs a packaged image, add it
  alongside and point `binpath` at the package instead.
- `protocol` describes the device's **data radio** (`LoRa` / `LoRaWAN` / `Wi-Fi`), not the OTA
  transport. BLE is the update channel for every device here.
- `application` is what the app compares against the version reported by the device to
  decide whether an update is offered — keep it accurate and bump it on every release.

> The old flat-format `sensors.json` (one version per device, no `versions` array) was
> removed. `sensors_v1.json` is now the only manifest — any tool still reading
> `sensors.json` must be pointed at it.

## Adding New Firmware

1. Create the device folder in the tree for its radio:
   - **LoRaWAN** → `LoRaWAN/<category>/<Device-Folder>/`, where category is `sensors`,
     `dataloggers` or `controllers`.
   - **raw LoRa** → `LoRa/<Device-Folder>/` — a flat, top-level tree with no category level.
   - **Wi-Fi** → `Wi-Fi/Sensors/<Device-Folder>/`.
2. Drop in `<Device-Name>.bin` and `<Device-Name>.png`.
3. Add an entry to `LoRaWAN/sensors_v1.json` using the schema above. For a new version of
   an existing device, append to that device's `versions` array instead of adding a new key.
4. Check that `binpath` and `photopath` match the real files exactly — paths are
   case-sensitive on the server and start at the repo root (`LoRaWAN/...`, `LoRa/...` or
   `Wi-Fi/...`).
5. If the folder previously held only a `.gitkeep`, delete that placeholder.
6. Commit both the binaries and the manifest change together.

### Adding a New Version to an Existing Device

A build that runs on the same hardware but behaves differently — changed uplink content,
changed reset behaviour, order-specific defaults — is a **new version of that device**, not
a new model. Keep the model number as it is and add to the `versions` array:

1. **Model number never changes.** No suffix in the JSON key or in `sensorName` —
   `MacSync_LPS_ToF_X1` stays `MacSync_LPS_ToF_X1`. The version string is the only thing
   that separates the builds.
2. **Bump the version** — `V1.0.0` → `V1.0.1` for a behaviour change on the same hardware.
   Append a new object to that device's `versions` array; leave the existing entries alone
   so units already in the field can still be matched to the image they are running.
3. **Never overwrite** an existing `.bin` in place — a rebuild gets the next version number
   and its own file.
4. **Photo** — reuse the device's existing `.png` when the hardware is identical; point
   `photopath` at that file rather than duplicating the image.
5. **Write down what the version contains** — add a row to that device's *version notes*
   table in this file, stating exactly how the behaviour differs. Nothing inside a `.bin`
   says what makes it special, so an undocumented build is unusable a few months later.
6. **Flag payload changes.** If the new version changes what the uplink bytes mean, say so
   in the version notes — the decoder and dashboard have to be told which version a unit is
   running.

### The `custom/` Folder — Non-Standard Builds Only

Each device folder may hold a `custom/` subfolder. **Only non-standard firmware goes in
it**; the shipping firmware always stays at the top level of the device folder, so the two
are never mixed up.

1. **Location** — `<Device-Folder>/custom/<Standard-Name>-<Version>.bin`, inside whichever
   tree the device lives in, e.g.
   `LoRaWAN/sensors/MacSync-LPS-ToF/custom/MacSync-LPS-ToF-X1-V1.0.1.bin` or
   `LoRa/MacSync_MPV/custom/MacSync_MPV_X1-V1.0.1.bin`.
2. **File name** — letters, digits, `-`, `_` and `.` only. **No spaces and no brackets.**
   `binpath` is fetched as a URL by the OTA app, so a name with a space or a `(` in it
   breaks the download. Rename such a file to the `<Standard-Name>-<Version>.bin` form
   before adding it to the manifest.
3. **Still the same model** — a `custom/` build keeps the device's model number and is
   listed as a version of that device in the manifest, with `binpath` pointing into
   `custom/`. The folder is how a human tells standard from non-standard at a glance; the
   version string is how the app tells them apart.
4. **Always document it** in that device's *version notes* table — a `custom/` build with no
   written description is unusable later.

Because every version of a device sits in one `versions` array, the app can offer a
`custom/` build for any unit of that model. Check the version notes before flashing. If a
build must never reach ordinary units at all, it needs its own model number rather than a
version bump.

## Known Issues

**Hyphen vs. underscore inconsistency.** Folder names always use hyphens, but file names
are mixed: `MacSync-LBS-TH/MacSync_LBS_TH_X1.bin` uses underscores while
`MacSync-LBS-ToF/MacSync-LBS-ToF-X1.bin` uses hyphens, and JSON keys use underscores while
folders use hyphens. Not a bug today because every path is written out explicitly, but it
will break any code that derives a path from a device name. The Wi-Fi tree adds two more
variants: its category folder is capitalised (`Wi-Fi/Sensors/` vs. `LoRaWAN/sensors/`) and
its device folder uses underscores (`MacSync_WiFi_TH_BS/`) rather than hyphens. The `LoRa/`
tree uses underscored device folders too (`LoRa/MacSync_MBS_TH/`) and has no category level
at all, so a path cannot be assembled from a device name and protocol alone — read it from
the manifest.

**`LoRa/` moved out of `LoRaWAN/`.** Raw-LoRa firmware used to live at `LoRaWAN/LoRa/` and
now lives in the top-level `LoRa/`. `sensors_v1.json` has been updated, but anything holding
a cached or hard-coded `LoRaWAN/LoRa/...` path — an older copy of the manifest, a script, a
CDN entry — still points at the old location and will fail to fetch.
